# 熊猫守望 PandaFlow 项目报告

> 面向成都大熊猫繁育研究基地高峰游览场景的游客体验与动物福利协同 Skills 解决方案包

- 赛道：2026 全球智能体大赛 B 赛道（文商旅体 Skills 解决方案包）
- 细分方向：旅游·文旅（cultural_tourism）
- 目标机构：成都大熊猫繁育研究基地
- 项目阶段：参赛原型设计
- 文档日期：2026-09-04

## 一、执行摘要

PandaFlow 是一套面向大型动物主题文旅场所的多 Skill 协同方案。它围绕“行前合规咨询—个性化路线—天气与动物福利调度—现场事件分诊—运营复盘”形成闭环，在改善游客体验的同时，将动物福利、安全约束和公开服务规则置于普通游览偏好之前。

本项目不是成都大熊猫繁育研究基地的官方系统，也不代表双方存在合作或授权关系。原型仅使用公开可核查资料、公开天气 API 和明确标注的合成数据。所有涉及客流、工单和运营成效的演示数据均为测试数据，不冒充企业内部数据。

当前原型已实现 6 个可独立触发的 Skill，由一个总控按业务状态编排。每个 Skill 均包含 SKILL.md、可执行逻辑、输入输出契约、资源文件、正常/边界/异常测试和来源追溯。核心决策由确定性规则执行；当前代码尚未集成语言模型，未来即使加入意图理解或表达层，也不得绕过安全与业务规则。

## 二、目标机构与公开事实基础

成都大熊猫繁育研究基地是成都市公园城市建设管理局管理的公益二类事业单位。大赛规则允许文旅集团、商业综合体、体育俱乐部、文化机构等作为目标对象，因此该机构符合“可识别行业代表机构”的范围。

以下事实均来自目标机构公开页面：

1. 游客服务包含实名预约、分时入园、观光车、讲解、导览、交通、医疗、失物招领和投诉等多个环节。
2. 不同季节的开放与清园时间不同，熊猫塔另有预约、容量和临时关闭规则。
3. 因恶劣天气、动物保育、场馆维护或园区管理，部分区域可能临时关闭。
4. 大熊猫喜凉怕热，基地会依据场馆、天气和动物状态采取遮阴、回收室内等保护措施。
5. 高龄老人、幼童、孕妇和行动不便者存在陪伴、设施和安全方面的特殊需求。
6. 基地承担生物多样性保护教育职能，并建设了公开科普资料库。

这些事实说明，游客需求并非单纯“推荐几个景点”，而是受预约资格、时间窗、路线、设施状态、天气、安全和动物福利共同约束的动态决策问题。

## 三、业务问题定义

### 3.1 已有公开证据支持的问题

- **规则复杂且会变化**：开放时间、预约要求、场馆容量、轮休和天气措施分布在不同服务页面与公告中。
- **游客体验与动物福利存在约束冲突**：游客希望看到户外活动的大熊猫，但高温和动物状态可能要求转入室内或关闭部分区域。
- **特殊人群需要差异化安排**：亲子、老人、孕妇、行动不便者不能套用同一条“热门打卡路线”。
- **现场事件需要分级处置**：医疗、走失、失物、票务、秩序事件的紧急程度和处理岗位不同。
- **科普内容需要真实性控制**：文旅讲解必须可追溯，不能把网络传闻包装成科学事实。

### 3.2 待通过原型验证的业务假设

- 将分散规则转化为可执行决策树，可以缩短客服查找和解释规则的时间。
- 将天气、场馆状态和人群约束合并计算，可以减少不可执行路线和现场反复改线。
- 统一事件分类与升级格式，可以提升工作人员理解工单的速度和一致性。
- 将每次输出与来源、规则和处置结果绑定，可以支持运营复盘和知识更新。

这些内容在报告中称为“原型假设”，不写成目标机构已确认的内部痛点。

## 四、目标用户与核心场景

### 4.1 目标用户

- 游客：国内游客、入境游客、亲子家庭、老人及其他需要辅助服务的人群。
- 游客服务人员：咨询、投诉、失物招领和现场协调岗位。
- 现场运营人员：负责区域状态、设施、秩序与安全协同的岗位。
- 运营管理人员：需要查看问题分布、规则命中和改进建议的管理者。

### 4.2 核心使用场景

在周末或节假日高峰期，一组带老人和儿童的入境游客提交参观日期、可用时间、语言和行动能力。PandaFlow 完成预约合规核验并生成路线。当天出现高温且某区域因动物福利要求轮休，系统调用天气数据、重新评估风险并调整路线。游览途中发生老人身体不适，系统将事件升级为人工处置并生成未发送的结构化处置草稿。结束后，运营复盘 Skill 汇总规则命中、改线原因和事件处置记录。

## 五、Skills 包设计

| Skill | 业务职能 | 核心能力 | 主要输出 |
|---|---|---|---|
| visitor-policy-check | 行前咨询 | 预约、时段、证件类型、特殊人群规则核验 | 合规结论、缺失字段、警告、来源 |
| accessible-itinerary-planner | 导览规划 | 基于时间窗、路线图和人群约束计算游览计划 | 分时路线、耗时、休息点、备选路线 |
| panda-knowledge-guard | 科普讲解 | 检索官方科普资料并进行来源与置信度控制 | 中英文讲解、引用、拒答说明 |
| welfare-risk-dispatcher | 现场运营 | 联合天气、合成客流、场馆状态和动物福利规则 | 风险等级、调度动作、重规划请求 |
| incident-triage-dispatch | 客服与安全 | 医疗、走失、失物、票务、秩序事件分类和升级 | 优先级、负责岗位、处置步骤、话术 |
| operations-review | 数据分析 | 聚合脱敏执行记录，识别高频问题和规则命中 | 日报、问题排名、改进清单、证据链接 |

6 个 Skill 覆盖咨询、导览、科普、调度、客服和数据六类职能。总控智能体不是第 7 个参赛 Skill，只负责识别当前阶段并按顺序调用上述能力。

## 六、端到端业务闭环

```text
游客提出需求
  → 预约合规核验
  → 个性化路线生成
  → 天气/场馆/动物福利风险检查
  → 正常继续，异常时重新规划或生成未发送的升级草稿
  → 现场事件分诊与人工升级
  → 脱敏记录进入运营复盘
  → 规则与服务改进建议
```

闭环同时产生两类价值：游客获得更可执行、更安全且有来源的服务；运营方获得结构化、可追溯、可复盘的决策记录。

## 七、技术方案概述

- 核心语言：Python 3.11。
- API：FastAPI，所有 Skill 同时暴露本地函数接口与 HTTP JSON 接口。
- 数据模型：Pydantic，统一校验输入、输出和错误结构。
- 外部工具：Open-Meteo 天气预报 API；无网络时使用带 `demo_data=true` 标记的固定样例降级。
- 业务规则：JSON 规则库，规则记录来源、访问日期、适用条件、输出动作和版本。
- 路线规划：基于园区节点图、时间窗和硬/软约束的确定性计算。
- 科普检索：仅使用已登记的官方知识条目；没有可靠条目时拒答。
- 测试：pytest，覆盖单元测试、契约测试、异常测试和多 Skill 集成测试。
- 演示：FastAPI 已提供 HTTP API 和预设场景；静态 Web 页面与 WorkHub 适配仍待实现。

## 八、知识蒸馏设计

公开材料不会只作为附件保存，而会经过以下链路进入 Skill：

```text
官方网页/公告/地图
  → 来源登记（URL、标题、访问日期）
  → 原子规则提取
  → 人工校核事实与适用条件
  → 写入版本化 JSON 规则库
  → 测试用例验证规则命中
  → Skill 输出返回 rule_id 与 source_id
```

每条规则分为三种状态：`verified` 表示来自公开来源；`inferred` 表示根据事实作出的产品推断；`demo` 表示仅用于演示的合成状态。三者不得混写。

## 九、量化指标与验证方法

由于没有目标机构内部基线，本项目不预先宣称真实降本比例。原型通过固定测试集和人工对照实验产生可复核指标：

| 指标 | 原型验收目标 | 验证方式 |
|---|---:|---|
| 规则型结论来源覆盖率 | 100% | 检查所有规则输出的 source_refs |
| 高风险事件人工升级率 | 100% | 执行医疗、走失等高风险测试集 |
| 输出契约合规率 | 100% | JSON Schema/Pydantic 契约测试 |
| 路线安全硬约束满足率 | 100% | 路线测试集自动断言 |
| 正常/边界/异常测试通过率 | 100% | 自动化测试报告 |
| 天气接口失败可解释降级率 | 100% | 模拟超时、错误响应和断网 |
| 端到端 Demo 时长 | 不超过 5 分钟 | 按最终演示脚本计时 |

人工效率对照采用同一组案例，分别执行“人工查阅公开页面”和“PandaFlow 输出”，记录完成时间、遗漏项和错误项。最终 PDF 仅填写实际测得的数据，并同时披露样本量和实验条件。

## 十、安全、合规与伦理边界

- 不收集或保存真实身份证号、手机号、健康信息等个人数据。
- 不访问目标机构内部系统，不伪造合作、授权、SOP 或实时客流。
- 不执行真实购票、退款、通知工作人员或紧急呼叫。
- 医疗相关功能只做事件分级和人工升级，不提供诊断或治疗建议。
- 对无法核验的动物状态、场馆状态和科普内容明确拒答。
- API 密钥仅通过环境变量注入，不写入代码、日志或演示材料。
- 所有合成数据在当前接口响应中显示 `demo_data=true`；未来界面也必须保留该标记。
- 锁文件固定和依赖漏洞检查仍是提交前待完成项，当前不得声称已有对应验证。

## 十一、Live Demo 设计

演示采用“一次正常流程、一次动态变化、一次高风险异常”的结构：

1. 输入入境亲子家庭及老人需求，触发预约核验。
2. 生成中英文、含休息点的游览计划。
3. 获取天气数据并注入区域轮休状态，触发风险调度和路线重排。
4. 询问未经官方证实的传闻，展示科普 Skill 的拒绝编造与来源返回。
5. 模拟老人身体不适，生成高优先级、未发送的人工处置草稿。
6. 展示本次会话的运营摘要、规则命中与证据链。

计划中的正式演示主动启用在线天气 API；备份模式使用固定天气响应，确保网络异常时仍能诚实展示降级能力。

## 十二、推广与商业闭环

PandaFlow 的可复用对象包括动物园、自然保护教育基地、博物馆和大型主题景区。通用能力由路线、规则、事件和来源引擎提供，机构差异通过知识与规则包配置。

潜在交付模式为：首次规则蒸馏与场景配置服务 + 年度规则维护 + 私有部署或 API 服务。当前参赛版本只验证技术和业务可行性，不声称已经产生合同、收入或真实客户成效。

## 十五、风险与应对

| 风险 | 应对 |
|---|---|
| WorkHub 格式尚未公开获取 | 核心保持平台无关；获得官方样例后只实现适配层 |
| 无真实客流和工单数据 | 使用明确标注的合成数据，不推导真实经营结论 |
| 公开规则更新 | 保存访问日期和规则版本；提交前重新核验高影响规则 |
| 现场网络失败 | 使用固定演示响应并标明降级；当前不实现“最后成功数据”缓存 |
| Skill 数量达标但质量不足 | 只提交 6 个高质量 Skill，每个均完成三类以上测试 |
| Demo 内容过多 | 固定单一故事线，将完整能力留在答辩材料 |
